## 内容(已确认)

**定位:设计性系统,非验证性求解器。** 传统求解器(最短时间找解 / 解数评难度、依赖完整关卡数据)被明确否定为目标;本系统为**尽可能符合人类行为模式的仿真玩家代理**,与**渐进式关卡规划器**构成闭环:

- **代理四要素**:参数集(人格档位)、内部状态、评估行为、操作行为
- **基于有限的、不完整的关卡进行操作**:给出可能的操作 + 操作后的游戏状态变化 + 对难易度的感知
- **反馈闭环**:上述数据作为关卡规划器的输入,渐进式评估并生成关卡后续内容

**求解器执行循环(2026-11-22 定稿,已实现①~④):**
①感知 → ②分析 → ③决策 → ④操作 →(⑤预期:前向模型已由决策产出的 forecast 承载,对账/惊讶度未实现)→ 回①;迭代单位 = 1 次拾取及其结算;出口 = 清空/槽满判负

**求解器设计结构(已实现,2026-11-23):**
- **感知边界**:感知集 = 有可见像素的 pile 牌(exposedArea > 0)+ 槽内牌;身份识别阈值 0.25(占位,两段式待定);未识别牌拷贝遮蔽 elementId;主观视图复用 Tile/TileDerived(拷贝 + 子集重算),隐藏牌对代理不存在
- **v3 等价定理背书**:感知子集重算的覆盖并集 = 真实并集 ⇒ 主观可点性精确等于真值(不确定只残留在身份与隐藏节点存在/揭示)
- **分析算子**(2026-11-23 设计者审阅后收敛:对外 `analyze()` 一个入口;`AnalysisResult` 自 2026-11-24 起只含③决策与④操作实际读取的数据(blockersOf / occludesOf / closureSize / derived / occlusion / groups / matches),遮挡边 / 自建深度 / 揭露效能决策不读、不随 analyze 计算,由 `analyzeStructure` 按需产出(编辑器调试面板与验收测试用);分析只接收主观视图,与真值的对账归 Runner 驱动侧与 tests):遮挡边/自建深度/揭露闭包(传递闭包大小)/可点性;同类归组(已识别牌按元素分组);揭露效能(独占遮挡口径:至少一像素仅由它覆盖,与移除语义精确对应;v1.6 起含**独占面积数据**——pair 分布保留 + 合计标量,消费端决定聚合/加权);**匹配消耗 v4 = 消除模拟的净占用峰值**(2026-11-24 设计裁定,见下)
- **匹配消耗 = 消除模拟的净占用峰值**(2026-11-24):对挖掘区(闭包(launcher) ∪ 闭包(target))做一次消除模拟,记录**额外槽位占用的峰值**。matchCost 单位 = 槽位格数,可与空槽数直接比较;`executable` 即 `峰值 ≤ 空槽数`。模拟规则:
  - 空槽视为无限——不因槽满中断,挖掘区内可合并的配对最终一定合并
  - 每步四阶段:牌入槽占位 → 统计占用(**峰值在此读取**)→ 检查匹配并消除 → 重新统计
  - 净占用 = 槽内总数 − 模拟开始时已有的槽内牌数;原有牌被用于配对时净占用随之下降(槽内已持伴、闭包仅 1 张时,额外占用 = 1——至少要 1 个空槽才能消掉已放入槽中的牌)
  - 从闭包外找伴**只找槽内的或当前可直接点击的**,不找被遮盖的——递归深度会超出一般人类的感知范围。🟡 *2026-11-25 修订为按来源区分,见下条「槽内牌来源规则」:本条现只适用于模拟带入槽内的牌*
  - **槽内牌来源规则**(2026-11-25 设计裁定)——槽内的牌能否配对、去哪找伴,取决于它的来源:
    - **原有的**(模拟开始时就在槽里):只在闭包内找伴。去闭包外找,等于在模拟本次匹配的过程中夹带一次无关的 close 操作
    - **模拟带入的**(挖掘途中从闭包里拿进来的):可以去闭包外找伴——为它清槽是挖掘的一部分(仍只找当前可点的)
    - close 型无闭包(一张槽内、一张当前可点),规则不涉及;hold 型的启动牌若是原有槽内牌,它等待的目标牌就在闭包里,不受影响
    - 直接后果:原有槽内牌在模拟中数量只会持平或减少,净占用的基数稳定;与旧实现相比,某些匹配的峰值会**更高**(例:槽内原有 36,算「49 配 67」时旧实现顺手把 36 跟 49 消了,那是另一次配对)——这是规则的正确后果
  - 模拟结束时剩余的牌额外记录(`residual`:伴被压或身份未知而出不去的牌)
  - 挖 launcher / target 时只拿各自闭包内的成员(实现时补的规则:否则挖 target 会顺手拿走 launcher 的遮挡者)
  - **本次配对的两张牌只跟彼此配**,不跟第三张同元素牌配——保证它们是作为一对离场的,峰值才是「完成这次配对」的消耗;为模拟带入的牌找伴时,不拿与配对牌同元素的牌
  - 启动牌 = 配对两张中获取成本最低者;获取成本(`flatCostOf`:槽内 0 / 可点 1 / 被压 1 + 闭包大小)**仅用于候选排序,不是消耗**
  - **需挖掘的配对是「近似挑的」**(2026-11-25 明确):报告里每个图案只留获取成本最低的一对需挖掘配对,真正消耗最小的那一对可能没被模拟过——A+B 让被挑中的那一对算得更准,但没有改变挑哪一对。**dig 梯「按需全量」已固定**(2026-11-25 第八会话入库;`DigOptions.fullScan`,缺省 `'all'`):dig 出手时才把这些图案的全部需挖掘配对各模拟一遍,再按原排序择优(分析阶段不算);实现为 `Analysis.makePairScanner`,与报告期同一条代码路径(`opportunityOf`),报告本身的数值不变。**展开范围是决定性参数**(14 元素档各 300 局,对「只在报告配对里选」逐局对照):展开报告里**所有有需挖掘配对的元素**(含报告配对不可执行的)→ 74.7% → 77.7%,输→赢 12 / 赢→输 3;只展开有可执行候选的元素 → 75.3%(6 / 4);只展开排序第一的候选所在元素 → 74.3%(2 / 3)。**收益几乎全部来自「报告说这个图案做不了,换一对却做得动」**:固定范围下 14 元素档 dig 出手 2218 次里有 88 次属于这种,另两档范围恒为 0 次。7 / 23 / 35 元素档通关率不变(100% / 6.0% / 0%),7 元素档槽压峰值 1.52 → 1.48;耗时 ×0.98 / ×1.25 / ×1.41 / ×1.36。与第七会话探针对照:过程量逐位吻合(dig 每次出手可选 35.56 / 9.44 / 3.60 条,记录为 35.6 / 9.4 / 3.6),终点 77.7% 对 77.0%;基线 74.7% 对记录的 73.3%,差 4 局——原探针未入库,无从核对(本次基线由改动前的编译树与新代码关掉开关各跑一遍,四档 1200 局选牌逐局一致)。**教训**:第一版实现把范围读成「只展开有可执行候选的元素」,测得 +0.7 个百分点(噪声内),直到拿记录里的过程量去对才发现读窄了——复述文字口径不够,要用过程量核对
  - **候选规则的推论**:挖掘区内那张同元素牌压着某候选时,它必不比被压者贵,会被选为 target(「中间的那张会被选为 target」,2026-11-24 设计者确认;穷举 57699 组几何核实)
  - 共同路径只计一次、可合并项的消化、+1 还是 +2,都不是显式规则,是模拟的自然结果
  - **拿牌策略:两组贪心各跑一遍,取峰值小者**(2026-11-25 设计裁定,方案「A+B」——更好的贪心规则,在多组顺序上各跑一遍)。起因:同一挖掘区、不同拿牌顺序会得出不同峰值——单次模拟拿到的不是可能的最小消耗(穷举核实:原单遍贪心在约 75% 的需挖掘匹配上高于真实最小值,平均高 1.6 格)。两种策略:
    - `dig-only`(即原行为):只挖闭包;挖某张牌时,其闭包内能立即闭对的成员优先,其余按 tileId 升序
    - `settle-first`:在 dig-only 基础上,挖掘途中若槽内**模拟带入的**牌有伴当前可点,先拿它进来消掉(腾槽)
    - 取舍:峰值小者;平分取 dig-only;再平分取拿牌少者。胜出策略记入 `MatchCostBreakdown.strategy`
    - 效果(60 个开局盘、467 条需挖掘匹配):与真实最小消耗的差距缩小 42%(平均每条高 1.58 → 0.91 格),非最优的匹配 74% → 60%,45% 的匹配消耗降低、无一升高;代价:耗时约 ×1.9,通关率几乎不变(14 元素档 72% → 73%,每档 100 局)
    - **⛔ 试过否决的方向**:①「主动清成对可点的牌」——拿大量与本次挖掘无关的牌,且会让启动牌/目标牌各自跟第三张同元素牌配掉,得到虚假的低峰值(两张都在闭包外的牌成对消掉,不可能降低闭包的峰值);②「先剪枝再模拟」(只模拟挖掘区相同的配对中的一条)——实测同元素配对的挖掘区重叠有限(去重后仍需模拟 78.8%),且挖掘区相同峰值未必相同
    - 局限:仍是贪心,60% 的需挖掘匹配高于真实最小值;达到真实最小值需搜索(约四分之一搜不完)
  - **计算方式(2026-11-24 提速,方案甲;规则不变)**:原实现每拿一张牌就把全盘遮挡重算一次(每次分析 33~113 次,占分析耗时 85%~92%)。现改为 `computeOcclusion` 拆出「收集遮挡关系」(`buildOcclusionIndex`)与「按移除集判被压」(`blockedAfter`),`analyze` 只收集一次并把索引放进 `AnalysisResult.occlusion`;模拟增量维护——初始取主分析结果,每拿一张牌只更新被它压着且仍被压的牌(P1 单调性)。与旧法逐字段等价(两层回归测试,旧模拟按原文留在 tests 作参照);每次分析 3.0 / 8.0 / 17.0 毫秒 → 0.56 / 0.70 / 2.32 毫秒(7 / 14 / 35 元素)
- **⛔ 已推翻的匹配消耗口径**(保留演进痕迹,均被 v4 取代):v2.2 获取成本 = 1 + (闭包+深度)/2 双口径平均;v2.3 递归定价(遮挡者成本递归;实测 dig 均值 9→86 分化过剧而回退,引擎已于 2026-11-24 移除);v3「闭包并集 − 严格可合并项 + 加项」公式(2026-11-24 设计者裁定:加多少项、剔多少对都是在近似一个本可直接算出的量)
- **MatchReport 配对保留**(2026-11-24 设计裁定):**两张都能直接拿到的配对(close / double 型)全部保留;需要挖掘的配对(hold / dig 型)每个元素留获取成本最低的一对**。起因:此前每元素只留获取成本最低的一对,slot-close 出手时 33%(7 元素)/ 12%(14 元素)的局面里另有同样能闭对却没被考虑的牌,pair-complete 出手时 44% / 18% 的局面里另有同元素可点却没被预演的牌。设计者先定「报告阶段保留全部、剪枝放到决策阶段」;实测对比后(四档各 500 局、同种子;14 元素档通关率 / 7 元素档槽压峰值 / 四档耗时):现状 66.8% / 2.15 / 64 秒,只展开 close / double 73.6% / 1.63 / 83 秒,「凡涉及槽内或可点牌的配对全留」74.6% / 1.58 / 164 秒,「全部配对都模拟」74.2% / 1.56 / 297 秒——**收益全部来自展开 close / double,再多留需挖掘的配对只增加耗时**,据此裁定取第一种。报告结构:`MatchReport.opportunities` 为全部保留的配对(按消耗 → elementId → 启动牌 → 目标牌排序),`byElement` 为按元素索引,`byType` 按配对计数。**决策侧**(设计者:「将需要做差分的所有牌统计起来做个去重」):slot-close 取全部 close 配对的目标牌,pair-complete 取全部可执行 double 配对里的牌,都按牌去重——同一张牌每次决策只做一次拾取差分(去重后每步预演 14 元素约 2.2 次、7 元素约 4.3 次);dig 排序在 elementId 之后补启动牌 / 目标牌的 tileId 作决胜键。**随同修正两处**:①匹配类型改看「能否直接拿到」(槽内或可点),不再看闭包大小——只被不足阈值的细条盖住的牌可点而闭包不为 0,此前它与槽内牌的配对会被记成 hold、slot-close 让位、dig 梯先把那丝牌拿掉(占据模型的盘面上不出现,任意叠放的盘面上会出现);②择优函数 `pickBestByDelta` 原以候选本身判「是否已有胜出者」,候选改为直接传 tileId 后数值 0 会被当成没有——改用 found 标记(此问题由新写法引入,在落地前被测试拦住)。效果(默认梯):14 元素档通关率 66.8% → 73.6%、23 元素档 5.6% → 7.4%(各 500 局),7 元素档槽压峰值 2.15 → 1.63;14 元素 500 局里 pair-complete 出手 9184 → 10356 次、dig 4412 → 3931 次、explore 350 → 280 次;四档各 100 局耗时 13.3 → 17.2 秒。AgentDebug 选中面板改为展示「本牌参与的最便宜配对」(仅类型检查,编辑器未实跑)
- **运行性能(2026-11-24,三步;产出逐项不变)**:①**只算决策要读的数据**——`AnalysisResult` 不再携带遮挡边 / 自建深度 / 揭露效能(③决策不读),需要时调 `analyzeStructure` 按需产出;同类归组记录去掉无人读的 `depth`。②**analyze 内不重复计算**——遮挡邻接 `blockersOf` / `occludesOf` 由遮挡关系索引导出(列表按感知序);闭包大小与匹配挖掘区共用同一次记忆化 DFS(不再另建 OcclusionTopology);归组只算一次。③**Board 增量刷新**(游戏核心)——`eliminate` 后不重算(只动槽内的牌);`pick` 后只重算被拿走那张牌直接压着的牌(全量刷新时重建牌堆的遮挡关系索引);构造 / 撤回 / 洗牌仍全量;对外接口不变,取走的状态仍是快照。效果:每次分析(开局盘)约 2~3 倍,默认梯四档各 100 局 38.8 → 13.3 秒,批量基线逐项不变。现状(14 元素,每步):预演里的 analyze 50%、顶层 analyze 36%、Board 操作 5%;单次 analyze 里消除模拟约六成。轮内预演缓存当前无命中(配对保留扩展后每步预演 14 元素约 2.2 次、7 元素约 4.3 次,已按牌去重、无重复);四档各 100 局在配对保留扩展后为 17.2 秒。回归:`tests/board-state.test.js`(每个操作后与全量重算逐值核对,盘面含 test_layout / 金字塔 / 随机堆叠 / 同层重叠合成盘)
- **决策 v1 = 扫描梯瀑布**(`Ladder.ts`,2026-11-23 定稿):决策以「扫描梯」模式围绕分析数据思考——梯为有序、可插拔的数组,依序过梯、首个非空胜出、全空走内置兜底;每梯产出 **AgentOperation = 移除动作 + 原因 + 预期**(结构化:rule / utility / runnerUp / delta / match;预期 = pairCompletes / slotAfter / exposes / confidence / forecast),预期即⑤阶段的对账面;Runner 增 v2 决策轨,随机 / 见对先拿策略保留为对照基线
